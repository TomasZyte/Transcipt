# Сравнение двух вариантов Whisper на sound2

`asr_test.py` — отдельный локальный клиент. Он не запускает Telegram polling,
не импортирует `bot.py` и не меняет production. Облако принимает запросы только
через ранее собранный отдельный `asr_comparison_handler.py`.

29.10.2026, 15:00 МСК: обе согласованные проверки завершены с `COMPLETED` и
`asr_validated=true`. WhisperX восстановил обе детские фразы владельца; прямой
faster-whisper large-v3 пропустил обе. Аудио и model-lock совпали, подсказки не
передавались. Это один фрагмент и две настройки одной модели: результат не
доказывает общее преимущество модели или только VAD. Диаризация отключена.
Прошли 78 тестов бота/клиентов, включая 20 тестов этого клиента. Исправлен
подсчёт health: `ready` пересекается с lifecycle-состояниями (`idle=1, ready=1`
означает один worker), поэтому ограничивается отдельно. Два и более worker,
занятая очередь, throttled и unhealthy по-прежнему блокируют отправку.
Пересечение `idle/ready` подтверждено живым API и примером
[официального RunPod](https://github.com/runpod/runpod-plugins-official/blob/main/plugins/runpod/skills/runpod/golden-paths/14-load-balancing-endpoint.md).

RunPod executionTime — 17.746 / 10.879 с, без утверждения о полном cold start
или стоимости. Перед каждым заданием биллинг за 1–29 октября показывал $0.075
тестовому endpoint; он отстаёт на час. Резервы оставлены полностью: $1.116 из $2.
Стенд выключен (Active/Max=0/0, ASR_COMPARISON_TEST=0); API подтвердил ноль jobs
inProgress/inQueue и workers. Журналы сохранены, обе попытки исчерпаны.

## Фиксированный эксперимент

| Параметр | Значение |
|---|---|
| Порядок | `wx_auto`, затем `fw_v3` |
| Аудио | один WAV, sound2 8.5–19.5 с, mono/16kHz/PCM16 |
| Модель | large-v3, ревизия `edaa852ec7e145841d8ffdb056a99866b5f0a478` |
| Endpoint / bucket | `tt17em69to6yua` / `poslovnica-test` |
| Образ | RunPod Release #15, коммит `2bd8f04`, `Dockerfile.asr-whisper` |
| Число отправок | максимум 2, по одной на вариант, без повторов |
| Таймаут задания / TTL | 120 / 240 секунд |
| Клиент / отмена | 270 секунд + до 20 секунд на отмену и проверку статуса |
| Резерв | $0.50 на каждую попытку, включая ошибочную/неопределённую |
| Плановый общий расход | $0.116 прежнего учёта + $1.00 резервов = $1.116 из $2 |

Это консервативное планирование, а не жёсткий долларовый лимит провайдера.
Холодный старт и задержка биллинга требуют наблюдения за workers и последующей
сверки счёта. Runtime test API key не умеет менять Max workers или получать admin
конфигурацию. Клиент отменяет известное задание, но не выключает endpoint.

## Приватные файлы и история

Фиксированный каталог: `.test-runtime/<TEST_BOT_ID>/asr-children-v1/`.
Его нельзя переименовывать/чистить для сброса лимитов. `campaign.json` закрепляет
SHA аудио, манифест, точный образ и хеши всех прежних журналов отправок/повторов.
Добавление, изменение или удаление старого журнала блокирует новый запуск до
ручной сверки. Старые резервы $2 сохранены в истории и не прибавляются повторно
к фактическому исходному учёту $0.116. Прямой UI показывал $0.075 для тестового
endpoint; сохранена более осторожная база, поскольку биллинг отстаёт.

Новые `jobs/message-asr-*.json` создаются с `fsync` **до POST /run**.
Потеря ответа без job ID не вызывает повторной отправки. Если ID известен,
при ошибке/таймауте выполняются `/cancel/{id}` и `/status/{id}`; одного ответа
на отмену недостаточно. Неопределённый статус блокирует дальнейшие отправки.
Обе попытки используют общий `runner.lock` с прежними тестовыми клиентами.

`fw_v3` разрешается только после проверенного `COMPLETED` первого варианта.
Сверяются хеш WAV, временные смещения, настройки, ревизия весов и SHA model-lock;
у двух результатов lock должен совпадать. При неверном ответе сырые данные
остаются для диагностики, но `asr_validated=false` блокирует продолжение.
Фразы детей не передаются в запросах. WER/DER по двум частичным эталонам не считается.

## Порядок согласованного запуска и запрет повтора

Описанные две попытки уже выполнены. Повторный `--submit` блокируется журналом;
не удалять записи и не создавать новый namespace для обхода лимита. Переданные
preflight сохранены отдельно, текущий preflight отражает выключенный стенд.
Новые варианты/задания требуют отдельного решения и сверки бюджета.

После явного согласования двух заданий оператор должен сверить UI RunPod:
точный endpoint/образ, Active=0, Max=1, GPU count=1, тариф не выше $1/ч,
execution timeout=120 с, idle=5 с, FlashBoot=false, ASR_COMPARISON_TEST=1.
Свежие показатели и разрешение записываются в `preflight.json` по шаблону.
Это **свидетельство проверки оператором**, не автоматическое чтение настроек API.
Запись действует 15 минут. Клиент дополнительно читает `/health` перед загрузкой
аудио и перед отправкой: очередь должна быть пустой, lifecycle workers не больше
одного; `ready` проверяется отдельно, поскольку это пересекающийся счётчик.

После этого к одной из команд выше добавляется `--submit`. Клиент загрузит только
выбранный WAV в тестовый R2, проверит скачанный SHA и создаст URL на 15 минут.
Подпись URL и секреты в журнал не пишутся. После каждого результата надо проверить
счёт и workers; перед вторым заданием обновить preflight при необходимости.
После завершения или ошибки вернуть Max=0 и выключить ASR_COMPARISON_TEST через UI.
При неясной отмене не удалять журналы и не запускать следующий вариант.

Клиент и документация пока локальные. Push в `codex/asr-build-check` вызывает
сборку тестового endpoint и здесь не выполнялся. Рабочие службы, main и Draft PR #2
не обновлялись.
