# Изолированный тест Telegram → R2 → RunPod

`integration_test.py` запускает обработчики бота для одного выбранного сообщения
одного пользователя в личном чате. Настройки читаются только из явно указанного
файла; `.env` приложения и унаследованные рабочие настройки не подмешиваются.
Обычный `bot.py` отказывается запускаться с `POSLOVNICA_TEST_CONFIG`.

## Подготовка

Нужны отдельный Telegram-бот, приватный бакет R2 с именем, заканчивающимся на `-test`,
и отдельный RunPod endpoint. Известные ID рабочего бота/endpoint и имя PoslovnicaBot
запрещены. При старте дополнительно сверяются Telegram ID и username через `getMe`;
существующий webhook не удаляется, запуск с ним отклоняется.

Ключ R2 должен разрешать чтение/запись только тестового бакета. Ключ RunPod —
GET/POST только тестового endpoint, включая `/run`, `/status` и `/cancel`, без GraphQL.
HF_TOKEN хранится в секрете **тестового** endpoint: локальный бот его не использует.
Права ключей и параметры GPU проверяются в консолях сервисов: runner не может
достоверно вывести их из строки ключа и не меняет настройки endpoint.

Для текущего стенда используются @TechnicalSpecBot, бакет `poslovnica-test` и
endpoint с тем же именем. Приватные ID и секреты остаются в локальном env-файле.
Сверить срок действия ключей перед следующим запуском.

Создать `.env.integration-test` по [integration.env.example](integration.env.example),
заполнить значения вручную. **Не перезаписывать уже существующий файл секретов**:
добавить недостающие `TEST_*`, удалить старый `DB_PATH`, оставить `PROVIDER_TOKEN`
и `LOCAL_BOT_API` пустыми, `STARS_ENABLED=0`.

Проверка конфигурации без сети, БД, polling и GPU (одна строка PowerShell):

```powershell
& 'C:\Users\Projects\Transcipt-git\.venv\Scripts\python.exe' 'C:\Users\Projects\Transcipt-git\tg-bot\integration_test.py' --env-file 'C:\Users\Projects\Transcipt-git\.env.integration-test' --check-config
```

## Один проверочный запуск

1. Убедиться, что старый тестовый polling остановлен. В тестовом endpoint проверить
   отсутствие незавершённых заданий и актуальную стоимость. Для уже согласованного
   GPU-прогона: Active workers = 0, Max workers = 1, только A5000/3090,
   idle timeout = 5 с, execution timeout = 600 с, FlashBoot выключен.
   Вне прогона Max workers должен оставаться 0. Рабочие ресурсы не изменять.
2. Отправить тестовому боту запись до **60 секунд и 10 МиБ**. Число спикеров
   определяется автоматически, `speakerCount` не задаётся.
3. Получить ID ожидающей записи следующей командой. Она проверяет Telegram identity
   и читает до 100 ожидающих updates без `offset`, не подтверждая их получение;
   выводит только ID/тип/размер/длительность медиа разрешённого личного чата.
   БД, R2 и GPU не используются. Не запускать одновременно с другим polling.

```powershell
& 'C:\Users\Projects\Transcipt-git\.venv\Scripts\python.exe' 'C:\Users\Projects\Transcipt-git\tg-bot\integration_test.py' --env-file 'C:\Users\Projects\Transcipt-git\.env.integration-test' --list-pending
```

4. Заменить `123` реальным `message_id` из результата. Команда ниже отправляет
   **платное** задание; запускать только в рамках согласованного прогона и бюджета.
   Сам polling подтверждает прочитанные updates, в том числе пропущенные сообщения.
   Если очереди больше 100 updates, не очищать её вслепую — сначала разобрать вручную.

```powershell
& 'C:\Users\Projects\Transcipt-git\.venv\Scripts\python.exe' 'C:\Users\Projects\Transcipt-git\tg-bot\integration_test.py' --env-file 'C:\Users\Projects\Transcipt-git\.env.integration-test' --message-id 123
```

5. После обработки runner отправит TXT в разрешённый чат и завершится. Проверить
   локальный журнал и RunPod `/status`/health: нет queued/in-progress jobs и workers.
   Вернуть **только тестовый Max workers в 0**, затем проверить фактические расходы.
   Эти настройки не меняются автоматически: у локального ключа нет GraphQL.

## Ограничения и остановка

- Остальные пользователи, группы, ссылки, платежи, админские команды и AI-кнопки
  блокируются до обработчиков. Доступны `/start`, `/help`, `/balance` и бесплатный
  экспорт своих результатов, пока процесс ожидает выбранное сообщение. Обычные
  меню могут отображаться, но остальные действия в этом режиме не выполняются.
- БД, временные файлы, логи, результаты и журнал размещены в
  `.test-runtime/<TEST_BOT_ID>/` относительно корня репозитория и исключены из Git.
  SQLite не связана с рабочей БД. Lock не допускает двух таких процессов одновременно.
- Каждый POST резервирует $0.50 **до отправки**. На весь сохранённый журнал разрешены
  не более `TEST_MAX_JOBS` (1–2) заданий; повтор того же `message_id` запрещён.
  `TEST_PRIOR_SPEND_USD + сумма резервов` не может превышать `TEST_BUDGET_USD` (до $2).
  `TEST_PRIOR_SPEND_USD=0.10` учитывает оценку двух прежних прогонов вне нового журнала;
  при появлении окончательного биллинга использовать его консервативную оценку.
  **Это ограничение запросов и планового бюджета, а не жёсткий лимит счёта RunPod.**
  Расход зависит от GPU, холодного старта и настроек endpoint; их нужно проверять.
- Для каждого задания задаются executionTimeout 600000 мс и TTL 900000 мс;
  локальное ожидание — 880 с, сессия polling — 1200 с. При таймауте, Ctrl+C или
  ошибке runner пытается отменить известный job ID, затем проверить его статус
  (до 20 с на попытку очистки). HTTP-ответ отмены сам по себе не считается завершением.
- Потерянный ответ POST оставляет запись `reserved` без ID; повторный POST запрещён.
  Неопределённый статус/неподтверждённая отмена блокируют следующие задания.
  Проверить RunPod вручную. Не удалять журнал ради повтора. Восстановление и сверка
  результатов после аварии пока не автоматизированы.
- Принудительное завершение процесса/выключение компьютера может прервать отмену.
  Оставшийся `runner.lock` удалять только после проверки PID, отсутствия процесса
  и сверки облачных заданий. До этого новые запуски должны оставаться заблокированы.
- После загрузки R2 runner читает presigned URL и сверяет SHA-256. Подписанные URL
  и секреты маскируются в логах. Сами аудио/расшифровки/журналы приватны, не коммитить.
  Объекты R2 автоматически не удаляются; TTL ссылки не является сроком хранения.
- Эти ограничения и удалённая отмена относятся только к `integration_test.py`.
  В обычном `bot.py` восстановление и отмена удалённого задания при таймауте ещё не реализованы.
