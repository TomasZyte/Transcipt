Все шесть вхождений повторяющейся двухсловной гипотезы получены в окнах

|---|---:|---:|---:|
| left-5 | 0,510 | −61,78 | 0,784 |
| right-10 | 0,679 | −50,70 | 0,811 |
| right-14 | 0,510 | −56,18 | 0,816 |

| right-33, финальное слово | 0,418 | −41,23 | 0,845 |

У первых трёх окон повторный decoder имеет avg_logprob примерно
−0,07…−0,19, то есть уверенно выбирает слова одновременно с высокой
оценкой отсутствия речи. В соседнем канале сигнал на 33–42 dB сильнее,
но этого недостаточно для вывода об эхе или о личности говорящего.
RMS — описательная мера, не основание удалять тихую речь.

Подтверждённое владельцем финальное слово восстановлено прежним вариантом
при no_speech_prob=0,845. Поэтому простой порог 0,6 удалил бы и полезный
результат. У ошибки в подтверждённой фразе 28–37 с CTC score ошибочного
слова 0,712: выравнивание не является независимой проверкой распознавания.

не пересекали эвристику 0,1. Новый план обрабатывает все исходные окна,
а не только уже обнаруженные низкие CTC score.

## Почему прежняя логика не исправила повторы

1. `channel_runs.callbacks` заменяет VAD на фиксированные маленькие окна
   и отключает их объединение. Каждое распознаётся отдельно.
2. В закреплённом [WhisperX 3.8.6 asr.py](https://github.com/m-bain/whisperX/blob/v3.8.6/whisperx/asr.py)
   batched-путь дополняет короткие входы до размера модели. Он возвращает
   текст/avg_logprob без обычного фильтра отсутствия речи. Одной сменой
   `asr_options.no_speech_threshold` этот путь не исправить.
3. `channel_repair.DECODER` намеренно отключает отбрасывание по тишине и
   оценкам, чтобы сохранить гипотезы. V2 выбирает больше целей, но для
   нескольких целей добавленные ±2 с остаются в основном тихим контекстом.
   Для left-5 повторный вход был 4,510 с, для right-10 — 4,679 с.
4. [faster-whisper 1.2.1](https://github.com/SYSTRAN/faster-whisper/blob/v1.2.1/faster_whisper/transcribe.py)
   в обычном пути отменяет пропуск по no_speech, если avg_logprob выше
   log_prob_threshold. При стандартном −1 приведённые повторы всё равно
   проходят. Менять порог вслепую опасно для коротких ответов.
5. Предыдущий текст не подсказывается: initial_prompt/prefix/hotwords=None,
   condition_on_previous_text=False. Обнаруженные повторы не объясняются
   переносом исправлений владельца или накопленным текстовым промптом.

Наиболее вероятный механизм: слишком короткий/слабый аудиосигнал допускает
устойчивую неверную гипотезу, а повтор почти того же входа её воспроизводит.
Из одних сохранённых результатов нельзя доказать все причины или обещать,
что более длинный контекст устранит каждую ошибку.

## Подготовленный алгоритм

`channel_context.py` сохраняет модель, настройки decoder и VAD из v2,
меняя способ подачи аудио. Ядра последовательных окон одного канала
объединяются до 24 с с сохранением всех исходных пауз. Добавляется до
3 с контекста с каждой стороны, максимум 30 с на блок. Длинное исходное
речевое окно сохраняется целиком. Каждый VAD-участок принадлежит одному
блоку; перекрывающийся контекст не даёт повторного экспорта тех же слов.

Распознавание использует native-путь того же загруженного WhisperX,
как предыдущий recovery. Отдельного первого прохода по микрофрагментам
и повторного цикла нет. Native-слова назначаются речевому окну только
при однозначном пересечении. Нет дробления слова по догадке. Неоднозначные,
неполные, находящиеся вне VAD или контекстные слова сохраняются в evidence.
CTC получает только полный исходный речевой участок и соответствующий ему
текст. Оценки/сомнения сохраняются, автоматический production-экспорт закрыт.

Для звонка подготовлено **17 блоков, 391,258 с суммарного аудио двух каналов**
с перекрытиями. Это объём входа, не GPU-время и не стоимость. Например,
left-5 получает блок 18,511–40,749 с вместо 0,510 с; right-10 —
49,865–78,987 с; финальный ответ — 181,186–187,776 с. Возможны потеря
тихих ответов и ошибки native-тайминга; только отдельная проверка модели
покажет, перевешивает ли контекст эти риски.

Лимиты: 32 блока на канал, 30 с на блок, 600 с всего. Все лимиты проверяются
до первого ASR-вызова. Данные не склеиваются с удалением пауз; каналы не
смешиваются; громкость не меняется; списка запрещённых фраз нет.

CLI только читает локальные WAV/сохранённый result и пишет новый JSON-план:

```powershell
.venv\Scripts\python.exe -X utf8 transcribe-backend\worker\channel_context.py --manifest .test-runtime\quality-2026-10-28\phone-call-2026-10-30\channel-speech-v2-input.json --saved-result .test-runtime\8357533895\channel-speech-v2\jobs\result-channel-speech-v2.json --output <новый-файл-плана.json>
```

Старый VAD используется только для оценки плана; будущий inference вызывает
VAD заново. Тексты, оценки и ручные поправки из сохранённого результата не
передаются decoder. Функция inference требует прежние тестовые флаги плюс
новый `CHANNEL_CONTEXT_TEST=1` и явно переданные callbacks. Модуль не
загружает веса, не обращается к облаку и не меняет окружение.
